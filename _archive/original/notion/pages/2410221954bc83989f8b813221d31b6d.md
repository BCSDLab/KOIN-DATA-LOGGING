## 원문 속성

```json

}
```

기준일: 2026-11-01 · 근거: 로깅 네이밍룰 v1.0 — DA1·DA2 공통 확정본, 로깅 통합 가이드, DA2 기능 사전, 화면 정의

새 로깅을 쓰는 사람이 위 문서를 다 읽지 않아도 같은 형식으로 쓰게 하려는 요약본이다. 충돌하면 확정본과 통합 가이드가 우선이다.

## 0. 3줄 요약

1. 라벨은 <code>service__page__feature[__detail]__category</code>, 4\~5구간이고 <b>마지막 구간은 항상 event\_category와 같다.</b>
2. <code>screen_view</code>는 라벨의 <b>두 번째 구간과 같은 고정 문자열</b>이다. 헤더는 <code>header</code>, 푸터는 <code>footer</code>.
3. 이미 구현된 로깅(품절 제보 등 동결 목록)과 승인된 category·value는 <b>이름을 정리한다는 이유로 바꾸지 않는다.</b>

## 1. event\_label 쓰는 법

```javascript
{service}__{page}__{feature}[__{detail}]__{category}
```

| 구간 | 의미 | 규칙 |
| --- | --- | --- |
| service | 서비스 | shop, cafeteria, bus, real\_estate, owner, timetable, board, callvan 등. 로그인 유도 팝업처럼 공용 요소는 account |
| page | 이벤트가 발생한 화면 | screen\_view와 같은 값. 이동·모달·팝업도 발생 시점의 화면명을 쓴다 |
| feature | 기능 | 사전에 있는 단어를 재사용한다. 없으면 사전에 먼저 등록한다 |
| detail | 세부 동작 (선택) | 최대 1구간. 없으면 생략하고 4구간으로 쓴다. category 단어로 끝내지 않는다 |
| category | 이벤트 종류 | 마지막 구간. event\_category 값과 같아야 한다 |

공통 문법

- 구간 구분은 <code>__</code>(밑줄 2개), 구간 안 단어 구분은 <code>_</code>, 전부 lower\_snake\_case.
- 라벨만 봐도 무슨 기능의 어떤 행동인지 알 수 있어야 한다.
- 검색어·품목명·ID 같은 <b>동적 값은 라벨에 넣지 않는다.</b> value에 넣는다.
- 기능만으로 충분하면 detail을 생략하고 마지막에 category를 둔다.

좋은 예 (현재 Event Log에 있는 라벨)

- <code>timetable__header__timetable_entry__header_entry__click</code> (시간표 2-3, 웹 헤더에서 시간표 진입)
- <code>shop__shop_list__search__click</code> (상점 목록에서 검색창 진입, 4구간)
- <code>bus__main__bus_entry__main_entry__click</code> (메인 홈 버튼)
- <code>account__shop_detail__login_popup__login_entry__click</code> (로그인 유도 팝업의 로그인 버튼)

나쁜 예

- <code>shop_detail_view_review_delete</code>: 옛 형식, 구간 없음
- detail 자리에 page 이름을 반복하는 <code>shop__shop_list__shop_list__scroll</code> 같은 라벨은 규칙 위반은 아니지만 피한다 (정리 기준 미결).
- detail이 category 단어로 끝나는 <code>...__search_click__click</code>은 금지.

### category 선택

기존에 승인된 category를 그대로 쓴다: click, select, scroll, swipe, toggle, exposure, submit, confirm 등.

- 이름을 정리한다는 이유로 category를 바꾸지 않는다. 전송 시점이 바뀌면 지표가 달라진다.
- 값은 따옴표 없이 <code>click</code>처럼 쓴다. 일부 DA2 페이지에 <code>“click”</code>, <code>click.</code> 표기가 섞여 있어 정리 대상이다.

### 예외 (이 목록만 규칙 밖)

- 버스 헤더·푸터 목적지형 라벨 4개
- 품절 제보 A/B 관련 동결 라벨 (<code>cafeteria__dining__soldout__*</code>, <code>cafeteria__dining__abtest__exposure</code> 등)
- 계정 5페이지의 <code>confirm__click</code>은 승인된 category 유지

## 2. screen\_view

- 일반 페이지: 라벨의 두 번째 구간과 같은 고정 문자열.
- 공용 헤더는 <code>header</code>, 공용 푸터는 <code>footer</code>. <code>{current_screen}</code> 같은 치환 표기를 쓰지 않는다. (2026-10-30 확정)
- 화면 이름은 화면 정의 문서에서 찾는다. 없으면 후보와 근거를 적고 검토중으로 표시한다.

## 3. event\_name

- 서비스 담당자 기준으로 <code>DA1</code> 또는 <code>DA2</code>를 <b>유지</b>한다. 합치지 않는다.
- DA1: 주변상점, 식단, 버스, 복덕방, 사장님, 팀원 모집, 시간표
- DA2: 계정·로그인, 게시판(분실물·시설물·쪽지), 배너, 콜밴팟, 모의수강신청, 학교 부서, 교내 시설물
- 새 서비스를 맡으면 로깅 통합 가이드의 서비스 배정표에 먼저 등록한다. 임의로 배정하지 않는다.

## 4. value / 추가 파라미터

DA1과 DA2의 value 표기가 다르다. <b>통일 기준은 미결</b>이라 아래는 임시 권장이다.

- 고정값은 그대로 쓴다. 예) <code>시간표</code>, <code>셔틀 탑승권</code>
- 동적값은 <code>{상점이름}</code>처럼 중괄호 변수로 쓰고 매핑 규칙을 적는다.
- 설명용 예시는 value 본문에 섞지 않고 별도 줄이나 검토사항에 쓴다. (DA1 value 145개 중 73개에 <code>(예: …)</code>가 섞여 있다.)
- 여러 값 후보는 <code>A / B / C</code>로 쓰되 실제 전송값을 명확히 구분한다.
- 개인정보·메시지 본문은 수집하지 않고 행동만 기록한다. (콜밴팟 메시지 본문 등)
- 검색어·입력 원문 수집은 별도 정책이 정해진 서비스만 한다. (현재 학교 부서 검색만 기록, 나머지 정책 미결)

## 5. 같은 라벨을 두 페이지에서 쓸 때

- 원칙: 라벨은 한 이벤트에 하나다. 같은 라벨이 필요하면 <b>동일 이벤트 계약표</b>(통합 가이드)에 등록한다. 기준 명세 1개와 대응 명세를 지정하고 서로 링크한다.
- 진입점이 다르면 detail이나 feature로 구분한다.
- 등록 전에는 병합하지 않는다. 호출 위치·대표 value·실제 전송 횟수 확인이 필요하다.
- 한 번의 사용자 동작에는 이벤트를 <b>한 번만</b> 보낸다. 중복 전송 방지 문구를 명세에 적는다. (iOS의 품절 제보 시작 이벤트가 같은 세션에서 0.2초 간격으로 반복된 사례가 있다.)

## 6. 페이지 양식

개별 명세는 아래 토글 구조를 쓴다. 토글 자식은 탭 들여쓰기 없이 쓴다.

```javascript
[이전 로깅]  원문 보존: 기존 label / value / category / 사진
[새 로깅 (YY.MM.DD)]
  - 설명 / 정확한 발생 시점:
  - screen_view:
  - event_name: DA1 또는 DA2
  - event_label: service__page__feature[__detail]__category
  - value:
  - event_category:
  [검토사항]  필요한 메모 + 통합 가이드 링크를 토글 하나에 정리. 빈 "- 없음" 항목 금지
  ### 참고사진  웹 | 모바일 두 칸, 각각 닫힌 토글
```

- 이전 로깅은 지우지 않는다. 라벨을 바꿨다면 <code>이전 label → 새 label</code>과 이유를 검토사항에 남긴다.
- 적용 플랫폼·작성일·화면명 근거를 본문에 반복하지 않는다. 플랫폼은 DB 속성으로 관리한다.
- 해당 없는 칸은 <code>해당 없음 (웹 전용)</code>처럼 사유와 함께 적는다.
- 상태(로깅 필요 / 진행 중 / 완료 / 레거시)의 "완료" 기준은 미결이다. 권장: 명세 검수 + 사진 완료 = 문서 완료, SDK 확인까지 끝나야 "개발 완료"로 따로 표기한다.

## 7. 참고사진

- <b>기능이 보이는 실제 화면</b>에 <b>코드로 빨간 네모만</b> 그린다. 문구·배치·해상도·테두리 밖 픽셀은 그대로 둔다. 생성형 이미지 편집은 쓰지 않는다.
- 웹은 파란색(기존 데스크톱 디자인), 모바일은 보라색(새 디자인)이 정상이다. 주변상점 모바일은 <b>모바일 환경으로 진입한</b> 화면이어야 한다. 가로폭만 줄이면 옛 파란 디자인이 나온다.
- 박스는 <b>라벨이 가리키는 요소</b>에 있어야 한다. (예: 셔틀 탑승권 로그에 유니버스 카드 박스 금지)
- 개인정보(휴대폰 번호, 닉네임, 계정, 이메일)는 마스킹한다. 010 번호는 사업자 개인 번호일 수 있다.
- 출처를 구분해 캡션에 적는다: 실제 앱 캡처 / 모바일웹 / 사용자 제공 / Figma. 모바일웹을 네이티브 앱 사진처럼 쓰지 않는다.
- 사진을 이동·삭제하지 않는다. 잘못된 사진은 보조자료 토글로 옮기고 사유를 적는다.

## 8. 작성 전 확인 순서

1. 화면 확인: 어느 화면의 어느 순간에 보내는지(클릭/선택/확인/제출) 먼저 정한다.
2. 사전 확인: feature와 행동 단어를 사전에서 찾고, 없으면 사전에 먼저 등록한다.
3. 라벨 작성 → screen\_view 일치 확인 → category 일치 확인.
4. 사진 첨부 → 마스킹 → 출처 캡션.
5. 저장 전 체크리스트로 점검.

## 9. 저장 전 체크리스트

- [ ] 라벨이 4\~5구간이고 소문자 snake\_case다
- [ ] 마지막 구간 = event\_category
- [ ] screen\_view = 라벨 두 번째 구간 (헤더 header, 푸터 footer)
- [ ] event\_name이 담당 서비스 기준(DA1 또는 DA2)이다
- [ ] feature·행동이 사전에 있는 단어다
- [ ] detail이 category 단어로 끝나지 않고 1구간 이하다
- [ ] 같은 라벨이 다른 페이지에 있으면 계약표에 등록했다
- [ ] 이전 로깅 원문과 사진이 보존됐다
- [ ] 플랫폼 속성이 맞고, 빈 칸에는 사유가 있다
- [ ] 사진 박스가 라벨 대상과 맞고 개인정보가 가려졌다
- [ ] 검토사항에 빈 "- 없음" 항목이 없다
- [ ] 동결 목록과 승인 category·value를 바꾸지 않았다

## 10. 하지 말 것

- 이름 정리를 이유로 category·value·발생 시점 변경
- 다른 서비스 담당자의 페이지를 상의 없이 대량 수정
- 문서를 정리했다는 이유로 "개발 완료"나 "수집 확인"으로 표기
- 새 라벨이나 새 feature를 사전 등록 없이 사용

## 11. 문서 완료와 개발 완료는 다르다

명세가 맞게 써져도 앱이 그 라벨을 보내는 것은 아니다. 문서 규칙이 확정된 뒤에도 아래는 개발 후 별도로 확인한다.

- SDK가 이 라벨·value·category·screen\_view를 실제로 보내는지
- 사용자 동작 한 번에 한 번만 보내는지 (중복 전송 여부)
- dbt/마트 매핑에 screen\_view·라벨 구간이 반영되는지
- 배포 후: 플랫폼·버전·적용일·이전→새 라벨을 기록하고 시점·값·화면명·중복·누락을 검수

BigQuery 확인 예 (읽기 전용): <code>kap-chat.mart.vw_mart_integrated_logs</code>에서 <code>event_label</code>로 조회한다. 마트는 하루 정도 늦게 갱신된다
