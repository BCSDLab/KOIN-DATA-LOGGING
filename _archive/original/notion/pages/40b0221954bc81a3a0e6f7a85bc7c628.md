## 1. 기본 규칙

- event\_label: <code>service__page__feature[__detail]__category</code> — 4\~5구간, 소문자 snake\_case.
- 구간 구분은 밑줄 두 개 <code>__</code>, 구간 안 단어 구분은 밑줄 한 개다.
- screen\_view는 라벨 두 번째 구간과 같은 고정 논리 화면값이다. 헤더는 header, 푸터는 footer다.
- 마지막 구간은 event\_category와 일치한다. 승인된 동결 예외는 원문을 유지한다.
- 서비스는 담당 기능 기준이다. 홈 화면에서 발생했다는 이유만으로 모든 이벤트를 main으로 바꾸지 않는다.
- 사용자 ID·검색어·상점명 등 동적인 값을 라벨에 넣지 않는다. 승인된 value·추가 파라미터 정책을 따른다.
- feature·detail은 [event_label 기능·행동 네이밍 사전](38b0221954bc831b912c012d8af2c857.md)을 재사용한다. 미등록 어휘는 먼저 정의하고 문서에 연결한다.

## 3. 명세 페이지 양식

최상위에는 <b>과거 로깅 / 새 로깅</b> 두 토글을 둔다. 과거 계약과 원문은 과거 로깅에 보존한다. 새 로깅에는 아래 여섯 항목과 현재 참고사진을 적는다. 작업 이력·이전/보조 사진 이력·발생 위치·기존 event\_label/value/category 같은 별도 설명 필드를 새 로깅에 반복하지 않는다.

```txt
과거 로깅
  기존 명세·전송값·발생 조건·추가 파라미터를 보존

새 로깅
  - 설명: 사용자가 어느 동작을 완료하거나 시도하는 순간인지 명시
  - screen_view: main
  - event_name: DA2
  - event_label: main__main__meal__click
  - value: {식사시간}_{클릭대상}
  - event_category: click
  참고사진: 웹 / 모바일을 구분하고 실제 대상을 빨간 네모로 표시
```

과거 계약이 없으면 과거 로깅에 ‘기존 로깅 없음’으로 적고 과거 값을 만들지 않는다. 명확히 다른 category를 구분해야 하는 경우 새 로깅 안에 동작별 소제목과 여섯 필드를 둔다. 예: 뒤로가기 click·swipe. 레거시 원문에 새 계약이 없으면 가이드 양식을 맞추려고 새 계약을 생성하지 않는다.

## 4. category와 value

기존 승인 category는 click·select·scroll·swipe·toggle·exposure·submit·fail이다. confirm은 category가 아니라 필요한 경우 detail이다. 버스 목적지형 라벨·품절 제보 등 승인된 예외를 일반 문법에 맞추려고 개명하지 않는다.

이름 정리만으로 category·value·발생 시점을 바꾸지 않는다. 클릭 시도와 API 성공, 화면 진입과 노출, 펼치기와 접기는 다른 조건일 수 있다. 추가·삭제가 실제로 없는 학기 편집처럼 명세가 제외한 행동은 보내지 않는다. 한 사용자 동작을 부모·자식 핸들러 또는 신·구 라벨로 이중 전송하지 않는다.

value는 고정값과 동적값의 의미를 구체적으로 적고 예시와 실제 전송값을 구분한다. 임의로 사용자 입력 원문 수집을 추가하지 않는다. 값 목록이나 성공 조건이 원문과 충돌하면 미확인으로 남기고 확정한다.

## 7. 동결·레거시와 플랫폼

- 팀원 모집 내부의 team\_recruitment\_\* 수집은 동결 범위로 유지한다. 공용 카테고리의 팀원 모집 진입은 별도 새 계약이다.
- 모바일 웹 상점의 Store/mobile·주문웹 이식 경로는 기존 shop\_\*를 유지한다. PC·공용 카테고리·헤더·푸터로 이 동결을 확대하지 않는다.
- 품절 제보 A/B 등 동결 계약은 기존 라벨·category·value·발생 시점을 보존한다.
- 새/미래 주변상점·졸업학점 계산기·동아리 레거시를 현행 명세로 자동 복원하지 않는다.
- platform은 실제 다중 선택 속성에서 WEB·WEB (모바일)·ANDROID·IOS를 구분한다. 웹 모바일 사진이 있다는 이유만으로 네이티브 앱 지원·SDK 검수가 끝났다고 표시하지 않는다.
- 한 페이지에 여러 계약이 있으면 속성은 포함된 계약의 플랫폼 합집합일 수 있으므로 각 계약의 설명·사진 범위도 확인한다.

## 8. 참고사진

현재 디자인의 실제 화면을 웹·모바일별로 확인한다. 모바일은 화면 크기만 줄인 PC 브라우저와 다르게 제공될 수 있으므로 실제 모바일 환경·사용자 에이전트를 확인하고 화면 로딩·데이터 표시가 끝난 뒤 촬영한다.

라벨이 가리키는 클릭·선택·스와이프 대상을 빨간 네모로 표시한다. 검색창과 검색 결과 행, 사진 열기와 넘기기, 홈 탭과 뒤로가기, 목록 정렬과 리뷰 정렬을 서로의 사진으로 대체하지 않는다. 제스처는 필요한 경우 방향 표시를 덧붙인다. 다른 플랫폼에 동일 동작이 없으면 해당 없음을 짧게 적고 가짜 클릭 위치를 만들지 않는다.

새 로깅에는 해당 플랫폼의 현재 사진을 표시하고 과거·보조 사진을 중복 나열하거나 별도 이력 토글을 만들지 않는다. 원본 이력은 과거 로깅 또는 별도 보관자료에서 관리한다. Stage 웹 사진은 네이티브 앱 실기기 사진으로 표시하지 않는다. 개인정보가 필요 없이 노출되지 않도록 확인한다.

## 9. 링크와 대표 명세

복사·이관으로 예전 페이지가 휴지통에 있으면 현재 트리의 대응 명세로 링크를 갱신한다. 카테고리처럼 여러 페이지가 대표 페이지에 합쳐졌다면 3-6 카테고리 내부 클릭 (현재 로깅) 2026.08.30 이후 찍히는 로깅 (원문 ID: 5ff0221954bc834abec001f49e73428e)으로 연결한다. 레거시 이력과 현행 구현 기준을 구분하며, 링크를 고치기 위해 휴지통 페이지를 무단 복원하지 않는다.

같은 동작의 대표·중복 명세를 구분하고 같은 클릭에 문서 수만큼 전송하지 않는다. 이름이 같아도 위치·시점·값이 다르면 같은 계약으로 단정하지 않는다.
