### 기능·행동 네이밍 확정 (2026-10-15)

- 별도 사전: [event_label 기능·행동 네이밍 사전](b7e0221954bc83608b1f8102fb3d2911.md). label만 읽어도 행동을 식별하도록 마지막 구간을 보완하며, 유사 기능은 동일 이름을 재사용한다.
- 공통 기능은 keyword\_manage / filter / search / contact / navigation 등으로 통일한다. 마지막 행동은 entry·open·select·confirm·response·submit·click 등으로 구분한다. 기능명 통일로 페이지명·기존 value·확정 시점을 바꾸지 않는다.
- 참고사진은 해당 로깅 바로 아래 토글에 넣고 원본·출처를 보존한다. 같은 이벤트를 이름 정리만으로 추가 전송하거나 보류 해제하지 않는다.

### 실제 화면 재확인 (2026-10-15)

- WEB 쪽지: 로그인 후 목록과 대화가 한 페이지에 함께 있고 대화 선택은 query만 바뀌는 것을 확인했다. 고정 화면명 chat 유지. 개별 명세와 화면 정의에 반영했다.
- WEB 모의수강신청: 로그인 후 예비수강과목 영역과 신청 버튼을 확인했다. 실제 신청은 실행하지 않았다. 고정 화면명 course\_practice 유지.
- Android 콜밴팟: 메인 모집 보기 → 목록 → 모집하기 → 출발지·도착지 선택창과 출발 시각 ‘확인’ UI까지 확인했다. 목록 전체·내 게시물에서 카드를 확인하지 못해 참여자·단체채팅·신고 및 참여·취소 모달은 실제 미확인 상태다. 카드 미표시 원인은 미확인이다. Figma 참고 표시는 해당 항목에 유지한다.
- 새 스크린샷으로 이미지를 교체한 작업은 아니며 기존 사진의 출처 표시는 보존했다. 실제 로그 전송·수집 검수는 이번 범위에 포함하지 않는다.

- 매 적용마다 네 키를 모두 보내고 기본·전체 상태는 ‘전체’로 쓴다. 단일 선택은 한국어 값 하나, UI가 허용하는 복수 선택은 중복 제거 후 정의된 순서로 ‘\|’ 연결한다. 예: filter\_item\_type=‘카드\|지갑’. 전체와 개별 값을 함께 기록하지 않는다.
- 11-22 필터 열기는 유지한다. 선택 도중이나 적용하지 않고 닫을 때 적용 로그를 보내지 않는다. 적용 횟수는 이벤트당 1회로 계산하고 항목을 펼친 행 수로 세지 않는다.
- 이력 비교: 기존 선택 이벤트와 적용 이벤트는 집계 단위가 다르다. 구현·배포 전환일과 이전→신규 대응을 기록한다.
- 개발 후속: 신규 네 파라미터의 SDK 전송·dbt 추출·마트 열 반영이 필요하다. 명세 변경만으로 기존 event\_value에 자동 반영되는 값이 아니다. 개발 반영 후 수집·중복 검수는 사용자 요청대로 후속 작업이다. 상세 값·기본값 규칙은 11-23을 따른다.

## 1. 시작할 때 확인할 기준과 변경 범위

Android 캡처를 모바일 대표 자료로 사용할 수 있으며 실제 실행한 플랫폼의 출처는 보존한다. 웹은 리디자인 전 데스크톱 웹뷰를 기준으로 한다. 실제 화면을 우선하며 접근할 수 없는 화면만 해당 플랫폼의 Figma로 보완한다. Figma를 근거로 작성하면 실제 화면·진입 경로 미확인을 표시한다.

## 2. 화면명과 event\_label을 만드는 규칙

<ol>
<li>
서비스명은 서비스 목록에서 고른다. 이번 분실물은 <code>board</code>, 로그인 안내 기능은 초안에서 <code>account</code>를 사용했다. 공용 채팅과 서비스 내부 쪽지는 범위를 구분한다.
</li>
<li>
페이지 구간은 클릭·선택·제출이 발생하는 화면에 대해 정의한 고정 이름이다. 도착 화면명을 진입 클릭에 사용하지 않는다. 2026-10-15 사용자 피드백: 기존 햄버거 디자인은 카테고리로 교체됐으므로 현행 명칭·label에는 category를 사용하고 과거 명칭은 이전 로깅에만 보존한다.
</li>
<li>
<code>screen_view</code>와 <code>event_label</code>의 두 번째 구간을 동일하게 맞춘다.
</li>
<li>
모달·팝업·다이얼로그·바텀시트·더보기 메뉴가 열려도 아래 화면명을 유지한다. 이런 캡처는 로깅 설명 이미지로 쓰며 별도 화면으로 등록하지 않는다.
</li>
<li>
<s>(취소)실제 별도 페이지로 이동하면 도착 후 발생한 이벤트부터 도착 화면명을 쓴다. Android와 웹의 구현이 다르면 플랫폼별 값을 명시한다. </s>
</li>
<li>
screen\_view, 즉 페이지명은 해당 로깅이 발생하는 화면 기준으로 로깅한다. 또한 이때 사용한 페이지명을 event\_label의 <code>{페이지}</code>에 사용한다. 
</li>
<li>
같은 기능이라도 실제 화면이 다르면 화면 구간을 나눈다. 분실물 수정은 <code>lost_item_edit</code>, 습득물 수정은 <code>found_item_edit</code>다.
</li>
<li>
공용 헤더·푸터는 사용자 합의에 따른 예외다. 발생 페이지와 관계없이 screen\_view와 event\_label 페이지 구간을 각각 header·footer로 고정한다. 카테고리는 모바일의 main\_category를 사용하고 WEB 속성에서 제외한다. 동적 화면명·치환용 변수는 사용하지 않는다.
</li>
<li>
화면 정의가 없거나 발생 화면이 미확인이면 노션에는 검토중으로 표시한다. 미정 화면·제안 이름은 별도 로컬 문서에 기록한다. 정의 확정 전에는 임의 이름이나 동적값을 screen\_view·event\_label 적용값으로 넣지 않는다.
</li>
<li>
event\_label만 보고도 어떤 이벤트인지 바로 알 수 있게 로깅한다. 
</li>
</ol>

## 3. 다른 서비스에서 진행할 순서

1. <b>대상과 범위를 고정한다.</b> 서비스·플랫폼·DB 뷰·항목 번호·변경할 필드를 정리한다. 이번에는 분실물 28개와 키워드 5개만 대상으로 삼고 공용 쪽지 4개를 제외했다.
2. <b>현재 문서를 읽고 백업한다.</b> 항목 ID, 이름, 속성, 전체 본문, 원본 이미지의 순서와 참조를 보관한다. 기존 상태나 사용자가 직접 수정한 필드를 확인한다.
3. <b>기존 로그의 의미를 파악한다.</b> 기존 label·category·value·설명·발생 조건을 함께 읽는다. 이름이 비슷하다는 이유만으로 다른 동작을 하나로 합치지 않는다.
4. <b>실제 화면과 진입 경로를 확인한다.</b> Android와 데스크톱 웹을 구분하고 본인/타인 게시물, 로그인 전/후, 입력 전/후, 모달 열린 상태 등 이벤트가 발생하는 상태를 확인한다.
5. <b>현재 화면명을 정한다.</b> 화면 정의와 대조하고 모달인지 별도 페이지인지 확인한다. 사용자 제공 캡처는 제공 자료라고 기록하며 직접 실행 확인한 것으로 표시하지 않는다.
6. <b>새 label을 작성한다.</b> 서비스·현재 페이지·기능·필요한 세부 구간 순서로 쓴다. 새/기존 label 대응표를 유지하고 동일 label을 재사용하는 경우 value로 구분하는 이유를 적는다.
7. <b>명세 초안을 작성한다.</b> 이전 로깅과 새 로깅을 분리한다. 화면명과 label을 채우고 category·value·트리거 변경 제안은 검토사항으로 분리한다.
8. <b>기능 표시 사진을 붙인다.</b> 해당 상태의 원본에 빨간 테두리만 표시한다. 추가 이미지에 있는 모달·필터·본인 게시물 캡처를 먼저 확인한다. 필요한 플랫폼만 배치한다.
9. <b>문서 검수를 한다.</b> 화면 구간의 일치, label 중복 의도, value 정의, 사진의 클릭 대상, 토글·컬럼 구조, 원본·속성 보존을 확인한다.
10. <b>담당자가 변경안을 확정한다.</b> 미정 화면명, category/value 변경, 트리거 대응, 적용 플랫폼, 보류 해제 여부를 결정한다. 실제 퍼널에 빠진 동작이 있으면 새 이벤트 제안으로 분리한다.
11. <b>개발 반영과 실제 수집을 검수한다.</b> 적용 버전·날짜·플랫폼과 이전→새 label 대응을 기록하고, 실제 동작과 수집값을 확인한다. 명세 작성 완료와 수집 검수 완료를 따로 표시한다.

진입 버튼, 선택 버튼, 적용/확인 버튼, 제출 버튼, 서버 결과는 서로 다른 시점이다. UI를 보기 위해 글 등록·삭제·신고·채팅을 실제 제출한 것으로 처리하지 않는다. 그런 동작이 별도로 필요하면 사용자 지시와 테스트 환경 범위에 맞춰 수행한다.

## 7. 빨간 박스 이미지 작업 방법

1. 원본과 항목 매핑을 저장한다. 같은 파일이라도 어떤 서비스·화면·로그·플랫폼의 근거인지 구분한다.
2. 현재 화면과 추가 이미지에서 해당 버튼이 실제로 보이는 상태를 선택한다. 타인 게시물에서 본인 전용 수정·삭제 버튼의 위치를 추정해 표시하지 않는다.
3. 코드로 원본 PNG의 복사본에 빨간 테두리를 그린다. 원본 파일을 직접 덮어쓰지 않는다.
4. 좌표는 해당 파일의 실제 크기를 기준으로 잡는다. 확대·축소된 미리보기 좌표를 원본 픽셀 좌표로 그대로 사용하지 않는다.
5. 표시본의 버튼·문구·상태를 눈으로 확인한다. 해상도와 빨간 테두리 밖 픽셀도 원본과 대조한다.
6. 같은 캡처를 여러 로깅에 사용할 때는 기능별로 다른 박스를 표시한다. 공유 이미지가 필요한 경우 사본 파일을 업로드한다.
7. 웹·Android 사진을 실제 플랫폼 범위에 맞춰 배치하고, 오래된 사진·공통 UI·Figma 근거를 표시한다.
8. 저장된 노션을 다시 읽어 사진이 해당 로깅 토글 안에 있고 원본 이미지가 유지되는지 확인한다.

이번 사례에서는 새 표시본 47개를 만들었다. 분실물·습득물 수정의 공통 이미지 두 쌍을 제외하면 고유 표시 파일은 45개였다. 기존 빨간 박스 캡처도 사본으로 업로드해 총 60개 이미지 블록을 새 로깅에 배치했다. 원본 로깅에 있던 이미지 95개는 유지했다.

## 9. 완료 판정과 실제 이벤트 검수

### 명세·이미지 단계

- [ ] 대상 항목과 제외 항목이 명확하다.
- [ ] 채택한 네이밍 체계와 변경할 필드가 명확하다.
- [ ] 최신 사용자 수정·기존 설명·속성·사진을 보존했다.
- [ ] 모든 항목의 screen\_view와 event\_label 페이지 구간이 같다.
- [ ] 모달·팝업은 원래 화면명을 유지한다.
- [ ] 플랫폼별 별도 화면과 수정 화면 분기를 반영했다.
- [ ] 같은 label의 재사용이 의도된 것이고 value 정의가 있다.
- [ ] category·value·트리거 변경 제안과 확정 사항을 구분했다.
- [ ] 사진의 실제 클릭 대상, 출처, 원본/공통/기존/Figma 여부를 확인했다.
- [ ] 새 사진의 위치·수·토글·컬럼과 실제 파일 접근을 확인했다.
- [ ] 보류 및 미확인 사항을 남기고 실제 로그 검증과 구분했다.

2026-10-12의 최종 문서 검수 기록은 분실물·키워드 33개 항목, 새 참고 이미지 60개, 기존 이미지 95개다. 각 항목의 원본 구간·DB 속성·요청 외 필드 보존, screen\_view/페이지 구간 일치, 사진 수, 본문 구조를 대조했고 저장된 검수 기록상 실패는 0개였다. 이는 실제 GA4 로그 발생 검증 결과가 아니다. category/value 의미와 UI 대응의 검토사항은 별도로 남았다.

근거: 로컬 <code>outputs/logging-renaming-guide-20261013/verification-summary.json</code>. 이 요약은 기존 검수 기록을 읽어 정리한 것이며 새 앱·데이터 검수 결과가 아니다.

### 개발 반영 후 수집 단계

실제 이벤트 검증이 요청되면 저장소 [AGENTS.md](http://AGENTS.md)에 따라 <code>kap-chat.mart.vw_mart_integrated_logs</code>를 기준으로 확인한다. 실행 전에 뷰 스키마와 날짜·시간·플랫폼 표현을 확인한다.

- <code>event_dt</code>, <code>platform</code>, <code>event_name</code>, <code>event_label</code>, <code>event_category</code>, <code>event_value</code>, <code>service_name</code>을 함께 대조한다.
- 과거 로그의 service\_name은 main/unmapped일 수 있으므로 서비스명만으로 필터링하지 않는다. 이전 label·category·value·플랫폼을 함께 찾는다.
- 동작 시점, 적용 플랫폼·버전·날짜와 이전→새 label 대응을 확인한다.
- 실제로 클릭/선택/제출한 동작과 수집된 값을 비교한다. 모달 취소와 확인, 선택과 적용, 제출과 서버 결과를 분리한다.
- 클라이언트에서 screen\_view와 label 페이지 구간이 일치하는지 확인한다. 통합 뷰에 화면 파라미터가 없으면 필요한 파라미터가 어디서 제공되는지 확인하고, 지침 없이 silver\_events로 대신 검증하지 않는다.
- 상태·값·중복·누락을 확인하고 구현·수집까지 검증한 항목만 완료 처리한다.

category·value·트리거 유지 또는 변경 여부:
시도한 방법과 실제 결과(성공 / 실패 / 미확인):
확정한 처리와 결정자:
