# KOIN 로깅 네이밍 기준 초안

## 1. 목적

KOIN 서비스의 로깅명이 기능별/작성자별로 다르게 정의되는 문제를 줄이고, 분석 가능한 형태의 일관된 이벤트 명세를 만든다.

이 문서에서는 다음을 정의한다.

- 로깅명 작성 원칙
- 현재 서비스별 로그 명세에서 정리 필요한 부분
- 서비스별 필수 로깅명 표
- 새 로그 추가 시 검수 기준

---

## 2. 로깅명 작성 원칙

### 2.1 이벤트명은 사용자 행동 중심으로 작성한다

이벤트명은 UI 위치나 동적 값이 아니라 사용자가 수행한 의미 있는 행동을 나타낸다.

좋은 예:

- <code>search</code>
- <code>search_result_click</code>
- <code>shop_detail_review_click</code>
- <code>bus_timetable_route_select</code>

피해야 하는 예:

- <code>click_search_button</code>
- <code>header_search_enter</code>
- <code>search_bus</code>
- <code>click_semester_20241</code>

### 2.2 동적 값은 이벤트명에 넣지 않는다

상점명, 게시글 제목, 학기, 학과, 검색어 등은 이벤트명이 아니라 파라미터로 전달한다.

예:

- <code>event_label</code>: <code>timetable_semester_select</code>
- <code>semester</code>: <code>20241</code>

### 2.3 네이밍은 lower\_snake\_case로 통일한다

모든 이벤트명, 파라미터명, enum 값은 <code>lower_snake_case</code>를 사용한다.

피해야 하는 예:

- <code>main_menu_moveDetailView</code>
- <code>main_bus_changeToFrom</code>

### 2.4 현재 구조에서는 event\_label을 표준 event\_key로 본다

현재 KOIN 로그는 실제 이벤트 식별자가 <code>event_label</code>에 들어가는 구조다.

따라서 단기적으로는 <code>event_label</code>을 표준 <code>event_key</code>처럼 관리한다.

장기적으로는 실제 GA4/Firebase <code>event_name</code>도 사용자 행동 중심으로 재정의하는 것을 검토한다.

### 2.5 event\_category는 행동 enum으로 제한한다

허용값 예시:

- <code>view</code>
- <code>click</code>
- <code>scroll</code>
- <code>select</code>
- <code>toggle</code>
- <code>submit</code>
- <code>success</code>
- <code>fail</code>
- <code>share</code>
- <code>back</code>
- <code>exit</code>
- <code>swipe</code>
- <code>notification</code>
- <code>file_upload</code>

### 2.6 개인정보/민감정보는 수집하지 않는다

검색어, 입력값, 게시글 제목, 학번, 이름, 전화번호, 이메일 등은 개인정보 포함 가능성이 있으므로 주의한다.

특히 GA4/Firebase로 전달되는 값에는 PII가 포함되지 않도록 마스킹 또는 미수집 기준을 둔다.

## 3. 현재 서비스별 로그 명세에서 정리 필요한 부분

### 3.1 공통

| 현재 보이는 문제 | 예시 | 개선 방향 |
| --- | --- | --- |
| 실제 이벤트 식별자가 <code>event_label</code>에 있음 | <code>event_name</code>은 팀명처럼 쓰이고, 실제 행동명은 <code>event_label</code>에 있음 | 단기적으로 <code>event_label</code>을 <code>event_key</code>로 표준화 |
| 플랫폼별 명세가 섞여 있음 | WEB/Android/iOS 값과 적용일이 한 행에 혼재 | 플랫폼별 필수/선택 여부와 적용 상태 분리 |
| 기존/신규 명세가 공존 | 기존 탭, NEW 탭, 옛날 탭이 같이 존재 | <code>status</code>, <code>deprecated_event_key</code>, <code>migration_note</code> 추가 |
| <code>event_category</code> 오기 가능성 | <code>click </code>처럼 공백 포함, 이슈 문서의 category 오기 | 드롭다운 enum 적용 |

### 3.2 버스

| 현재 보이는 문제 | 예시 | 개선 방향 |
| --- | --- | --- |
| 이벤트명이 UI 위치/이동 방식에 가까움 | <code>main_bus_changeToFrom</code>, <code>main_bus_scroll</code> | <code>bus_main_type_select</code>, <code>bus_main_type_scroll</code>처럼 행동 중심으로 정리 |
| 출발지/목적지/버스 타입이 <code>value</code>에 문자열로 섞임 | <code>한기대 / 천안역 / 야우리</code>, <code>학교셔틀 / 대성고속 / 시내버스</code> | <code>departure</code>, <code>arrival</code>, <code>bus_type</code> 파라미터로 분리 |
| 시간표 선택 이벤트의 입자도가 섞임 | <code>bus_timetable</code>, <code>bus_timetable_area</code>, <code>bus_timetable_citybus_route</code> | <code>bus_timetable_type_select</code>, <code>bus_timetable_area_select</code>, <code>bus_timetable_route_select</code>로 통일 |

### 3.3 식단

| 현재 보이는 문제 | 예시 | 개선 방향 |
| --- | --- | --- |
| 같은 이벤트명에 선택값을 <code>value</code>로 넣는 방향은 좋으나 파라미터 의미가 모호함 | <code>main_menu_corner</code> / <code>A코너</code>, <code>menu_time</code> / <code>아침</code> | <code>corner_name</code>, <code>meal_time</code>, <code>meal_day</code>처럼 의미 있는 파라미터로 분리 |
| 알림 토글 값이 문자열로만 표현됨 | <code>on/off</code> | <code>toggle_state: on/off</code>로 고정 |
| 공유/외부 이동 이벤트가 기능명 중심으로 섞임 | <code>menu_share</code> | <code>dining_share_click</code>, <code>dining_external_open_click</code>처럼 목적별로 분리 |

### 3.4 게시판/공지사항

| 현재 보이는 문제 | 예시 | 개선 방향 |
| --- | --- | --- |
| 이벤트명이 도메인/대상/행동 기준으로 일관되지 않음 | <code>notice_hot</code>, <code>inventory</code>, <code>short_cut</code> | <code>notice_popular_item_click</code>, <code>notice_list_item_click</code>, <code>notice_shortcut_click</code>로 정리 |
| 게시물 제목/키워드가 value에 들어감 | <code>(공지명)</code>, <code>(키워드)</code> | 가능하면 <code>notice_id</code>, <code>keyword_id</code>를 우선 사용하고 제목/키워드는 PII 검토 |
| 검색 입력값 저장 방식이 별도 표기됨 | <code>[검색 키워드] 입력값</code>, <code>mysql에 저장</code> | GA4/Firebase 전송 여부와 내부 DB 저장 여부를 명세에서 분리 |
| 알림 이벤트와 클릭 이벤트가 같은 계열 이름을 공유함 | <code>keyword_notification</code> | <code>keyword_notification_receive</code>, <code>keyword_notification_toggle</code> 등으로 분리 |

### 3.5 주변상점

| 현재 보이는 문제 | 예시 | 개선 방향 |
| --- | --- | --- |
| <code>value</code>에 동적 값과 행동 설명이 섞임 | <code>scroll in {카테고리}</code>, <code>check_delivery_{카테고리}</code> | <code>category_name</code>, <code>filter_name</code>, <code>toggle_state</code>로 분리 |
| 필터별 값이 이벤트명/값에 흩어짐 | <code>check_card_{카테고리}</code>, <code>check_bank_{카테고리}</code> | <code>shop_filter_toggle</code> / <code>filter_name</code>으로 통합 |
| 상세 페이지 이벤트가 너무 긴 prefix를 반복함 | <code>shop_detail_view_review_report_done</code> | <code>shop_review_report_submit</code>처럼 짧고 행동 중심으로 정리 |
| 이탈/뒤로가기/스와이프가 category와 current\_page에 섞임 | <code>click</code>, <code>swipe</code>, <code>logo</code>, <code>{카테고리}</code> | <code>shop_detail_exit</code> / <code>exit_type</code>, <code>destination</code>으로 정리 |

### 3.6 로그인/회원

| 현재 보이는 문제 | 예시 | 개선 방향 |
| --- | --- | --- |
| 같은 로그인/회원가입 이벤트가 기존/신규 명세에 중복됨 | <code>complete_sign_up</code>, <code>login</code>, <code>hamburger_login</code> | <code>auth_signup_success</code>, <code>auth_login_success</code>, <code>auth_login_click</code>로 통합 |
| source가 이벤트명에 섞임 | <code>hamburger_login</code>, <code>(웹)메인_헤더_로그인_클릭</code> | <code>source: hamburger/header/main</code> 파라미터로 분리 |
| 자동 로그인, 아이디 찾기, 비밀번호 찾기 입자도가 섞임 | <code>auto_login</code>, <code>find_id</code> | <code>auth_auto_login_success</code>, <code>auth_find_id_click</code>, <code>auth_find_password_click</code>로 정리 |

### 3.7 시간표

| 현재 보이는 문제 | 예시 | 개선 방향 |
| --- | --- | --- |
| 동적 값이 이벤트 value에 합쳐짐 | <code>click_semester_{학기}</code>, <code>click_curriculum_{학과}</code> | <code>timetable_semester_select</code> / <code>semester</code>, <code>timetable_curriculum_click</code> / <code>department_name</code> |
| event\_category에 보이지 않는 문자/오기가 섞인 흔적 | <code>\bclick</code> | 드롭다운 enum으로 입력 제한 |
| 이탈 이벤트가 여러 방식으로 흩어짐 | 뒤로가기, OS스와이프, 햄버거 이동 | <code>timetable_exit</code> / <code>exit_type</code>, <code>destination</code>으로 통합 |

### 3.8 졸업학점 계산기

| 현재 보이는 문제 | 예시 | 개선 방향 |
| --- | --- | --- |
| 파일 업로드 방식이 이벤트명/값에 섞임 | 경로 지정, 드래그&드롭 | <code>graduation_calculator_excel_upload</code> / <code>upload_type</code> |
| 학과/학기 선택값이 value 문자열에 합쳐짐 | <code>학과 드롭다운_{선택 학과}</code> | <code>department_name</code>, <code>semester</code> 파라미터로 분리 |
| 이탈 이벤트가 출구별로 쪼개짐 | 로고, 헤더, 푸터, 뒤로가기, OS 스와이프 | <code>graduation_calculator_exit</code> / <code>exit_type</code>, <code>destination</code>으로 통합 |

## 5. 새 로그 추가 시 체크리스트

- 이벤트명이 사용자 행동 중심인가?
- <code>lower_snake_case</code>인가?
- 동적 값이 이벤트명에 들어가지 않았는가?
- <code>event_category</code>가 허용 enum에 포함되는가?
- 필수 파라미터가 정의되어 있는가?
- 파라미터 타입과 예시 값이 있는가?
- 개인정보/민감정보 가능성이 검토되었는가?
- WEB/Android/iOS 적용 범위가 명확한가?
- 기존 이벤트와 중복되지 않는가?
- 분석 목적이 명확한가?
