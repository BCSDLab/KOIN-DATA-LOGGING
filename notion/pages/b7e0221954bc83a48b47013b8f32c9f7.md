## 2. 다른 서비스 작업 순서

1. [화면 정의 및 로깅 검수](6510221954bc83c380f90140afd0f4a7.md)의 ‘화면 정의 작업 기준’과 이 문서를 읽고, 기존 서비스의 명세 형식을 확인한다.
2. 대상 서비스와 플랫폼, 웹뷰 범위, 작성 위치를 확인한다. 이미 합의된 Android·데스크톱 웹 기준을 매번 다시 질문하지 않는다.
3. 실제 서비스를 열어 각 화면의 진입점을 확인한다. 실제 페이지 이동인지, 기존 화면 위의 팝업인지 구분한다.
4. 직접 확인한 화면은 캡처하고, 접근할 수 없는 화면만 Figma로 보완한다. 데이터·권한·로그인 등 접근 불가 사유를 기록한다.
5. 커서를 제거하고 필요한 크기로 다시 캡처한다. 파일의 실제 형식·해상도·글자·아이콘·상태를 확인한다.
6. 화면별 최신 이미지 한 장을 넣어 간결한 명세를 작성한다. 팝업 이미지는 별도 로깅 참고 토글에 둔다.
7. 노션은 가능한 범위만 수정한다. 이미지가 포함된 기존 구간의 교체가 막히면 새 하위 페이지로 완성된 정리본을 제공하는 방식을 사용한다.
8. 저장한 노션 페이지를 다시 읽어 화면 수, 이미지 수, 토글·컬럼 구조, Figma 표시, 이미지 파일의 접근 가능 여부를 확인한다.

화면을 보기 위해 모집글·채팅·신고를 실제 제출한 것으로 처리하지 않는다. 이번 작업에서는 모집글 작성이나 신고 제출을 실행하지 않았다. 데이터가 없으면 접근 불가로 기록한다.

## 3. 최종 명세에 남길 내용

- 화면별 필수 항목: 플랫폼, 화면 이름, 주 진입점, 최신 이미지 한 장.
- 필요한 경우만 추가: Figma 근거·프레임 링크, 실제 화면·진입 경로 미확인 표시.
- 서비스 단위로 짧게 기록: 확인일, Android 기준, 이미지 개선 여부, 공통 접근 불가 사유.
- 웹을 확인하지 못했다면 <code>web(데스크톱): 미확인</code>으로 적는다. 진입점을 못 찾았다는 이유로 서비스가 없다고 확정하지 않는다.
- 모달·팝업 참고 이미지는 화면 정의 수에 포함하지 않는다.
- 원본 이미지와 처리 프롬프트는 별도 산출물로 보관한다. 원본·개선본·중간 캡처를 최종 명세 안에 중복으로 늘어놓지 않는다.
- 화면 이름 제안과 실제 <code>screen_view</code>·<code>page_view</code> 값 및 로그 발생 검증은 구분한다. 화면 정의 완료만으로 로깅 검수 체크박스를 완료 처리하지 않는다.

## 4. 캡처 품질을 확보하는 방법

### 커서와 클릭 표시 제거 — 이번 작업에서 성공

1. 화면 이동을 끝낸 후 휴대폰과 연결의 메인 창에서 앱 창 바깥에 위치한 중립적인 제목 표시줄을 클릭한다.
2. 커서를 움직이지 않고 KOIN 앱 창을 다시 앞으로 가져온다.
3. 새로 캡처한 이미지에 커서와 파란 강조 표시가 없는지 확인한다.

최대화한 앱 창에서는 PC 여백에 커서를 두고 휴대폰 화면 영역에 포함되지 않도록 했다. 과거 작업의 좌표를 그대로 재사용하지 않는다. 창 위치와 크기, 캡처 영역을 매번 확인한다.

다음 작업에서는 가능한 한 큰 창이나 직접 얻을 수 있는 원본 캡처를 먼저 사용한다. 확장자나 문서 표시 크기만 바꾸는 것으로 화질이 개선됐다고 판단하지 않는다. 파일 형식을 확인하고 그 형식에 맞는 확장자와 업로드 MIME을 사용한다.

업스케일링을 사용할 때는 다음을 대조한다.

- 한글 문구, 날짜·시각·인원 등 숫자.
- 버튼·아이콘과 배치, 색상, 선택·비활성 상태.
- 팝업 높이와 배경의 가림 상태, 원래 화면 구성.
- 커서, 클릭 표시, PC 제목 표시줄·불필요한 여백의 포함 여부.

ImageGen 결과는 새로 생성된 비트맵이므로 무가공 원본이라고 표시하지 않는다. <code>선명도 개선본</code>이라고 짧게 표시하고 원본을 보관한다. 원본에서 읽을 수 없는 문구를 추정해 새 글자로 채우지 않는다.

## 6. 노션 작성·교체 시 채택할 방법

- 글만 바꾸는 작은 수정은 기존 페이지를 읽고 고유한 텍스트를 기준으로 범위를 좁혀 수정한다. 이번 작업에서 텍스트 기준의 작은 수정은 성공했다.
- 이미지가 포함된 구간의 교체가 실패해도 페이지 전체를 다시 쓰지 않는다. 자동 승인 거절 뒤 같은 효과를 내는 우회 실행도 하지 않는다.
- 하위 페이지를 사용한다면 화면별 최신 이미지와 최소 정보로 완성한다. 기존 서비스 본문에 같은 내용을 추가하는 것과 구분한다.
- 이미지는 업로드한 파일이나 노션의 안정적인 <code>notion-file-block://</code> 참조를 사용한다. 만료되는 다운로드 URL을 문서의 이미지 주소로 바꾸지 않는다.
- 페이지 생성·수정이 비동기로 접수되면 완료 상태를 확인한 뒤 결과 페이지를 읽는다. 접수만으로 성공을 보고하지 않는다.
- 본문에 이미지 표시가 9개 있다는 확인과 파일 9개가 실제로 접근 가능하다는 확인을 별도로 수행한다.
- 생성 여부가 불명확하면 먼저 기존 페이지와 하위 페이지를 확인한다. 같은 정리본을 다시 만들어 중복시키지 않는다.
- 사용자가 교체를 맡겠다고 했으면 정리본 링크와 짧은 완료 안내를 제공한다. 이후 최종 위치를 다시 확인하며, 사용자가 옮기거나 삭제한 임시 페이지를 임의로 복원하지 않는다.

콜밴팟에서는 하위 페이지 생성 후 화면 정의 7개와 이미지 9개를 다시 읽었고, 파일 다운로드 참조 9개가 모두 해결되는 것까지 확인했다. 후속 조회에서는 상위 원문에 정리된 명세가 있고 임시 하위 페이지는 삭제 상태였다. 현재 참고할 예시는 [화면 정의 및 로깅 검수](6510221954bc83c380f90140afd0f4a7.md)의 콜밴팟 항목이다.

## 7. 완료 확인

- [ ] 실제 Android와 데스크톱 웹 범위를 구분했다.
- [ ] 실제 화면과 Figma 보완 항목을 구분했다.
- [ ] 화면마다 이름·플랫폼·진입점·최신 이미지가 있다.
- [ ] 팝업을 별도 화면으로 세지 않았다.
- [ ] 원본을 별도로 보관하고, 개선본임을 표시했다.
- [ ] 커서·클릭 표시가 없고 글자가 읽힌다.
- [ ] 같은 화면의 중복 이미지와 작업 경과를 최종 명세에서 걷어냈다.
- [ ] 노션의 토글·컬럼·이미지와 실제 파일 접근을 확인했다.
- [ ] 실제 로그 검증을 하지 않았다면 완료했다고 적지 않았다.

실제 이벤트 검증이 요청되면 저장소 지침에 따라 <code>kap-chat.mart.vw_mart_integrated_logs</code>를 기준으로 별도 검수한다. 이번 콜밴팟 화면 정의 작업에서 실제 로그 값·발생 여부를 검증한 것으로 간주하지 않는다.
