## 1. 적용 범위와 기준 우선순위

- 현재 DA2 리네이밍 범위: 계정·로그인, 게시판, 배너, 분실물, 콜밴팟, 쪽지·채팅, 모의수강신청, 학교 부서 정보, 교내 시설물. 이 범위의 새 명세 <code>event_name</code>은 <code>DA2</code>로 고정한다.
- 서비스별 이전 로깅은 과거 자료로 보존한다. 다른 서비스의 담당자 코드·보류 상태·수집 조건까지 일괄 변경하지 않는다. 졸업학점 계산기는 레거시로 현행 리네이밍 대상에서 제외한다.
- 사용자 확정 사항을 우선한다. 공통 규칙은 이 문서, 기능·행동 용어는 사전, 서비스별 정확한 발생 조건·값·플랫폼·보류 여부는 개별 최신 명세를 따른다. 서로 다르면 임의 추론으로 덮어쓰지 않고 검토 현황에 차이를 남긴다.
- 과거 개선안의 행동형 event\_name, 단일 밑줄 label, 퍼널 단계 삽입, 확장 enum은 현재 규칙으로 자동 채택하지 않는다. 원문은 [로깅 문서 이력 · 개선안](0950221954bc83caaf63810fd27cac92.md)에서 확인한다.

## 3. event\_label 네이밍

<code>{서비스명}__{페이지}__{기능}__{세부기능 또는 행동}</code> — 지정된 DA2 작업 서비스에는 네 번째 구간까지 필수로 적용한다 (2026-10-16 확정).

- 구간 구분자는 <code>__</code>, 구간 안 단어 구분자는 <code>_</code>다. 각 구간은 영문 소문자·숫자를 사용한 <code>lower_snake_case</code>로 쓴다. <code>DA2</code> 담당자 코드와 한국어 value까지 소문자 코드로 바꾸는 규칙은 아니다.
- 마지막 세부기능·행동 구간은 필수다. <code>title_entry</code>, <code>phone_click</code>, <code>search_submit</code>처럼 label만 보고 기능과 행동을 파악할 수 있게 작성한다. 앞의 기능 구간만으로 의미가 충분하면 마지막 구간에 해당 event\_category 값(예: <code>click</code>, <code>select</code>, <code>submit</code>)을 넣어도 된다. 기존에 구체적인 행동이 있으면 그대로 유지한다. 정확히 네 구간으로 작성하고 빈 마지막 구간을 허용하지 않는다.
- 유사 기능은 [event_label 기능·행동 네이밍 사전](38b0221954bc831b912c012d8af2c857.md)의 같은 기능명을 재사용한다. 예: <code>keyword_manage</code>, <code>filter</code>, <code>search</code>, <code>contact</code>, <code>navigation</code>. 화면명까지 기능명과 함께 바꾸지 않는다.
- 물품명·검색어·선택값·게시물 ID·시간·학기·제목처럼 변하는 값은 label에 끼워 넣지 않는다. <code>value</code> 또는 확정한 별도 파라미터에 기록한다.
- 이름 통일만으로 이벤트를 합치거나 추가 전송하지 않는다. 같은 행동·의미·시점으로 묶는 경우에는 허용 value와 적용 범위를 명시하고 결정 이력을 남긴다.
- 서로 다른 명세가 같은 UI에 대응할 수 있다. 학교 부서 1-0-2와 공통 3-6은 별개 유지가 확정됐으므로 상호 링크와 기능 차이를 남긴다. 확정된 분실물 11-18·11-23 통합은 개별 명세와 결정 현황을 따른다.

### event\_category와 세부 행동의 관계

아래는 기존 공통 네이밍 문서의 기본 목록이다. 리네이밍 작업에서는 개별 명세의 승인된 category를 보존한다. 이 표에 없는 값이나 변경이 필요하면 먼저 검토 사항으로 기록하며 임의 변환하지 않는다.

| event\_category | 뜻 | 언제 쓰나 | 예시 event\_label |
| --- | --- | --- | --- |
| click | 버튼·메뉴·탭·항목을 누름 | 대부분의 버튼·탭 클릭. 화면을 나가는 버튼(뒤로가기·이탈)도 포함 | <code>shop__shop_list__shop</code>, <code>cafeteria__dining__soldout__photo</code> |
| select | 여러 선택지 중 하나를 고름 | 코너처럼 정해진 보기 중 하나를 고르는 행동 | <code>cafeteria__dining__soldout__select</code> |
| scroll | 목록·화면을 스크롤함 | 스크롤 동작 1번(손을 떼거나 멈출 때)마다 1회 | <code>shop__shop_list__list</code> |
| swipe | 화면을 손가락으로 밀어 넘김 | 스와이프 제스처로 화면을 나갈 때 | <code>shop__shop_detail__back</code> |
| submit | 입력한 내용을 제출하는 버튼을 누름 | 제보처럼 양식을 최종 제출하는 버튼 | <code>cafeteria__dining__soldout__submit</code> |
| fail | 제출한 내용이 처리되지 않음 | 제출 버튼을 눌렀지만 실패했을 때(서버 응답 기준) | <code>cafeteria__dining__soldout__submit</code> |
| exposure | 화면에 자동으로 보여짐 | 사용자가 누르지 않아도 화면 진입 시 A/B 안이 보일 때 | <code>cafeteria__dining__abtest__exposure</code> |

세부 행동과 category는 같은 시점을 설명해야 하지만 문자열이 항상 같아야 하는 것은 아니다. <code>search_submit</code>은 검색 아이콘·Enter 실행을 구체적으로 표시하는 label이며, 확정된 개별 명세의 category는 유지한다. <code>entry</code>·<code>confirm</code>·<code>response</code> 등을 category의 신규 enum으로 자동 추가하지 않는다. 제출 버튼 클릭과 서버 성공·실패 응답, 사용자 클릭과 자동 노출도 구분한다.

## 4. 화면 정의·플랫폼·이미지

### 발생 시점의 고정 화면명

- 실제 화면명은 [화면 정의 및 로깅 검수](0e40221954bc823d92c301f83b5f68d0.md)에서 확인한다. screen\_view와 event\_label 두 번째 구간은 로깅이 발생하는 그 시점의 고정값으로 일치시킨다. 클릭·선택·제출 시점에 보이는 화면을 기준으로 판단한다.
- 모달·팝업·다이얼로그·바텀시트·더보기·토스트·키보드는 별도 화면으로 정의하지 않는다. 모달에서 버튼을 눌러도 그 아래 화면명은 유지한다. 이미지는 로깅의 발생 조건을 설명하는 참고 자료로 둔다.
- 공용 헤더·푸터만 예외다. 발생 페이지와 관계없이 screen\_view와 label 페이지 구간을 각각 <code>header</code>·<code>footer</code>로 고정한다.
- 동적 화면명이나 치환용 변수를 적용값으로 사용하지 않는다. 정의가 없거나 발생 화면을 확인하지 못한 항목은 Notion에 검토중으로 적는다. 후보명·근거는 로컬 <code>docs/screen-definition-review-20261015.md</code>에 기록하고, 확정 전에는 임의 이름을 적용하지 않는다.
- 분실물·습득물 수정 화면은 <code>lost_item_edit</code> / <code>found_item_edit</code>로 구분한다. 11-29·11-30은 2026-10-16 사용자 확인으로 현행 적용 대상이며 보류 문구를 제거했다. 다른 항목의 보류 상태는 별도 확정 없이 변경하지 않는다.

### 플랫폼과 근거

- mobile은 ANDROID·IOS 공통 디자인을 뜻한다. DB 속성에는 해당되는 두 값을 각각 지정한다. 실제 검수·캡처 기준은 Android이며 Android 확인을 iOS 실행 검수로 표시하지 않는다.
- 모바일은 현재 리디자인 화면, WEB은 리디자인 전 데스크톱 화면을 기준으로 한다. 좁은 반응형 웹을 실제 앱이나 데스크톱 웹 캡처로 혼동하지 않는다.
- 현행 카테고리·콜밴팟은 WEB이 없어 속성에서 제외한다. 카테고리 명칭을 사용하고 과거 햄버거 표기는 이전 로깅에만 보존한다. 부서 내부 분류나 분실물 필터를 공용 카테고리와 혼동하지 않는다.
- 모의수강신청은 WEB만 제공한다. 시간표 진입 클릭의 화면은 <code>timetable</code>, 서비스 내부는 <code>course_practice</code>다.
- 실제 실행 화면과 진입 경로를 먼저 확인한다. 로그인·권한·데이터 등으로 접근할 수 없는 화면만 해당 플랫폼 Figma로 보완한다. 사유·프레임 링크와 <code>Figma 참고 / 실제 화면 미확인</code>·실제 진입 경로 미확인을 표시한다.

### 사진과 설명 배치

- 화면 정의는 플랫폼·화면 이름·주 진입점·최신 대표 이미지 중심으로 간결하게 유지한다. 확인일·근거·접근 불가 사유는 필요한 만큼만 적는다.
- 로깅 참고사진은 해당 로깅 바로 아래 토글에 배치한다. 웹·모바일이 모두 지원되면 구분하고, 미지원과 미확인을 구별한다. 추가 이미지의 모달·필터·본인 게시물 캡처를 먼저 확인한다.
- 기능 표시는 원본 복사본에 코드로 빨간 테두리만 추가한다. 글자·배치·색상·상태·원본 해상도와 테두리 밖 픽셀을 유지하고 원본은 별도 보관한다.
- 글자가 읽히는 크기로 캡처하고 커서·파란 클릭 표시·불필요한 PC 여백을 제외한다. 선명도 개선본은 원본과 대조하고 개선 사실을 표시한다. 문구나 UI를 추정해서 채우지 않는다.

## 6. 리네이밍 작업 순서

1. 대상 서비스·플랫폼·DB 항목 번호·변경할 필드를 정한다. 로컬 화면 기준·플레이북과 이 문서, 최신 개별 명세를 먼저 읽는다.
2. 최신 원문을 백업한다. ID·속성·설명·기존 label·category·value·보류 상태·이미지 순서와 참조를 보관한다.
3. 기존 로그의 목적과 발생 시점을 파악한다. 이름이 비슷하다는 이유로 다른 행동을 합치지 않는다.
4. 실제 Android·데스크톱 웹과 진입 경로·로그인 여부·본인/타인 게시물·선택/확인 상태를 확인하고 화면 정의와 대조한다.
5. 고정 화면명과 label을 작성한다. 기능·행동은 사전을 재사용하고 이전→새 label 대응을 남긴다. category·value·트리거 변경은 확정 사항과 제안을 구분한다.
6. 이전 로깅은 유지하고 새 로깅 초안을 채운다. 지원 플랫폼과 출처에 맞는 기능 사진을 해당 로깅 아래 토글에 넣는다.
7. 문서·속성·이미지·보류 상태와 변경 대응표를 검수한다. 담당자가 확정할 항목은 번호와 구체적인 선택·확인 시점으로 남긴다.
8. 개발 반영 시 버전·날짜·플랫폼을 기록하고 별도로 수집을 검수한다. 현재 작업의 중복 전송 및 개발 후 수집 검수는 사용자 요청으로 후속 단계다.

## 7. 개별 명세 양식

개별 로깅 본문은 이벤트 설명·발생 조건·필드와 참고사진 중심으로 작성한다. 적용 플랫폼은 DB 속성에서 관리한다. 적용 플랫폼·범위·작성일·수정일·화면명 근거를 본문에 반복하지 않는다. 검토·참고 메모는 ‘검토사항’ 토글 하나로 모으고, 남은 검토는 결정·검토 현황에 원문 링크와 함께 기록한다.

아래는 작성용 템플릿이다. 실제 값·근거를 채우며 기존 DB 속성과 보류 상태는 요청 범위 안에서만 수정한다.

```txt
<details>
<summary>이전 로깅</summary>
	[기존 설명·label·value·category·메모·이미지를 원래 순서대로 보존]
</details>
<details>
<summary>새 로깅 ([작성일]) — 초안 또는 확정 상태</summary>
	- 설명: [현재 화면에서 어떤 조건으로 어떤 동작을 했는지]
	- 발생 시점: [선택 / 선택하기 / 확인 응답 / 제출 / 서버 결과 중 정확한 시점]
	- screen_view: [정의된 고정 화면명]
	- event_name: [명시적으로 확정한 담당자 코드]
	- event_label: [서비스__현재페이지__기능__세부기능또는행동(필수)]
	- value: [한국어 고정값 / 선택값 / 정의한 동적값]
	- event_category: [기존 승인값 또는 별도로 확정된 값]
	- 추가 파라미터: [키·타입·기본값·예시, 해당할 때만]
	<details>
	<summary>검토사항</summary>
		[검토·참고 메모와 통합 검토 목록 링크]
	</details>
	<details>
	<summary>참고사진 (기능 표시)</summary>
		[WEB / mobile 구분, 이미지와 실제·제공·공통·Figma 출처]
	</details>
</details>
```

개발 전달 대응표에는 항목 ID·이전/새 label·screen\_view·category/value 유지 또는 변경·발생 시점·플랫폼·결정 상태·적용 버전과 날짜를 남긴다. 같은 label을 선택값으로 구분하면 허용 value를 함께 정의한다.

## 8. 완료 기준

### 명세·화면·이미지 단계

- [ ] 실제 화면과 Figma 보완·미확인·보류를 구분했다.
- [ ] 발생 화면의 고정명과 label 페이지 구간이 같고, 헤더·푸터·모달 기준이 맞다.
- [ ] event\_label이 빈 구간 없이 정확히 네 구간이며, 기능·행동을 파악할 수 있고 사전을 재사용했다.
- [ ] 같은 label의 재사용·통합·별개 유지 이유, value·추가 파라미터·정확한 발생 시점을 적었다.
- [ ] 플랫폼·최신 사용자 수정·기존 원문·사진·보류 상태를 보존했다.
- [ ] 사진이 해당 로깅 아래 토글에 있으며 대상·출처·화질·파일 접근을 확인했다.
- [ ] 저장한 페이지를 다시 읽고 토글·컬럼·이미지 수·참조·링크를 확인했다.

### 개발 반영 후 수집 단계 — 별도 후속

실제 이벤트 검증이 요청되면 저장소 지침에 따라 <code>kap-chat.mart.vw_mart_integrated_logs</code>를 기준으로 조회한다. 스키마·날짜·시간·플랫폼 표현을 먼저 확인하고 <code>event_dt</code>, <code>platform</code>, <code>event_name</code>, <code>event_label</code>, <code>event_category</code>, <code>event_value</code>, <code>service_name</code>을 함께 대조한다.

과거 service\_name은 main·unmapped일 수 있어 서비스명만으로 필터링하지 않는다. 이전 label·category·value·플랫폼과 적용 버전·날짜를 함께 확인한다. 화면 파라미터가 통합 뷰에 없으면 제공 위치를 확인하며 지침 없이 silver\_events로 대신 검증하지 않는다. 실제 동작의 시점·값·누락·중복까지 검증한 항목만 수집 완료로 표시한다.
